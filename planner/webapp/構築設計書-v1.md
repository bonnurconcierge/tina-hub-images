# Tina専用 手帳アプリ 構築設計書 v1（仮称: 光庭手帳）

作成日: 2026-09-23（水）
役割分担: Tina = オーナー・最終判断 / 上位Claude = 構成（この文書）/ 下位エージェント = 実装・運用（12章の発注書）
姉妹文書: `planner/README.md`（Notion手帳の構成）、`planner/AGENT_HANDOFF.md`（Notion手帳の運用分担）

読者は2種類。①発注を受けて実装するエンジニアAI（迷ったらこの文書を正とする）②非エンジニアのオーナーであるTina（全体像と判断の経緯を確認する）。

事業OSファミリー（AI Alert Concierge 構築設計書-v2、Pocketチャレンジ 構築設計書-v1）と同じ技術基盤（Supabase＋Vercel＋PIN）と体制（司令塔＋サブエージェント発注）を踏襲する。車輪の再発明はしない。

---

## 0. このアプリの憲法（迷ったらここに戻る）

1. **三者のいいとこ取りであって、三者の全部載せではない。** 紙・デジタル・Notionのそれぞれが一番得意な場面でだけ、その流儀を使う（1章の表が判断基準）
2. **開いて10秒で「今日」が分かる。書くのは1日3行まで。** 書く量を増やす機能は作らない
3. **正本は1つ。** 予定はGoogleカレンダー、タスクとプロジェクトはこのアプリ、長文の記録はNotion。同じ情報を2か所で編集させない
4. **スマホ一台・回線が切れても回る。** 2027年3月からのジョージア長期滞在（回線瞬断あり・時差5時間）で使えることが最低条件
5. **Tina固有のルール（定例・5つの流れ・気学・季節）はコードに書かず、データとして持つ。** 商品化と、上位エージェントが構成だけを変えられるようにするため
6. **朝ハブ・夕ハブの自動生成は壊さない。** アプリはまず「読む側」から入り、書く役割は段階的に引き取る
7. 毎日使われなかった画面は削る。足すより削る

## 1. 何のいいとこ取りか（機能の採用基準）

| 出どころ | 残したい良さ | アプリでの形 | 捨てるもの |
|---|---|---|---|
| 紙の手帳 | 見開きの一覧性。時間が身体感覚で分かる。手で書く儀式。線を引く・丸で囲む自由さ。ページをめくる安心感 | 週・月は固定レイアウトの「見開き」。今日の3行。手書きレイヤー（iPad＋Apple Pencil）。年間は1本の帯 | 書き直せない。検索できない。持ち歩く重さ。過去の集計ができない |
| デジタル手帳 | 検索。繰り返し予定。通知。チェックの集計。どこでも同期 | 定例はデータ（rrule）。習慣のヒートマップ。Telegram通知。PWAで同期・オフライン | 予定とタスクが1画面に混ざって圧迫する。通知が多すぎる。テンプレが多すぎて選ぶのに疲れる |
| Notionのプロジェクト管理 | 構造化（DB・リレーション）。ビュー切替。AIエージェントが読み書きできる。長文の記録 | プロジェクト／タスク／イベントは正規化したDB。5つの流れ・状態のボード。エージェント用API（jobs） | ページを開く回数が多い。読み込みが遅い。手帳として毎日開く気持ちにならない。構造を作り込みすぎる誘惑 |

判断に迷ったら「その機能は、上の表のどの列の良さを守るためか」を1行で言えるかで決める。言えなければ作らない。

## 2. 位置づけ（既存の仕組みとの関係）

```
朝ハブ・夕ハブ（Notion・自動生成）  ─ 読む ─▶  ┌──────────────┐
Googleカレンダー（予定の正本）        ─ 同期 ─▶  │  光庭手帳      │ ◀─ Tinaがスマホ／iPadで開く
TODO.md（現在のタスク正本）           ─ 段階的に引き取る ─▶│  (PWA + Supabase) │ ─▶ Telegram通知
Notion手帳（年間イベント／ボード／月間）─ 初期データ・ミラー ─│              │ ─▶ Notionミラー（週1）
方位盤画像（tina-hub-images）         ─ 画像URL ─▶      └──────────────┘ ◀─▶ 下位エージェント（jobs）
```

- **今回作ったNotion手帳（planner/README.md）はこのアプリのプロトタイプ**。画面の骨格（年間イベント・プロジェクトボード・月間ページ・週の型・振り返りの型）はそのまま画面設計に引き継ぐ。Notion側はアプリ稼働後、閲覧用ミラーと長文記録に役割を絞る
- 朝ハブ・夕ハブは残す。アプリの「今日」画面は朝ハブの要約を表示し、夕方はアプリで書いた3行と繰越を夕ハブに渡す（Phase 2）
- 事業OSファミリーで固まった型（PIN、Supabaseテーブル設計の作法、Phase分け、Telegram通知）を流用する

## 3. 全体アーキテクチャ

### 3.1 構成

```
【画面】 Vercel 上の PWA（Vite + Preact + TypeScript）
         ・ホーム画面に追加して全画面で開く（iPhone／iPad／Mac）
         ・IndexedDB（Dexie）に全データを持ち、オフラインでも読み書きできる
         ・オンライン復帰時に Supabase と同期（フィールド単位の最終更新勝ち）
              ↕
【保管】 Supabase（PostgreSQL・無料枠）
         ・単一ユーザー。RLS で anon キーからは自分の行だけ
         ・Realtime は使わない（同期は起動時と5分ごとのポーリングで十分）
              ↕
【頭脳・同期】 Tinaの Mac（launchd）＋ Claude Code（既存の朝ハブ・夕ハブと同じ経路）
         ・カレンダー同期スクリプト（Python・gws CLI）: 1日2回＋手動
         ・朝ハブ生成時に days テーブルへ要約を書く
         ・jobs テーブルをポーリングして下位エージェントが動く
              ↕
【通知】 Telegram Bot（既存の bridge を再利用）
```

### 3.2 なぜこの構成か

- Supabase＋Vercel＋PINは事業OSの共通基盤。Alert Concierge・Pocketチャレンジと同じ運用手順・同じ障害対応で回せる
- PWAにしたのは、App Storeを通さず、スマホのホーム画面から紙の手帳のように「開く」体験を作れるため。ネイティブアプリは作らない
- フロントは既存の資産（静的HTML＋vanilla JS）より一段だけ上げる。4画面・オフライン・手書きを素のJSで書くと保守が重くなる。PreactはReactの書き味で軽く、静的サイトとしてVercelにそのまま置ける
- Mac側のlaunchd＋Claude Codeを「頭脳」に据えるのは、Googleカレンダー・Notion・Gmailの認証がすでにそこに揃っているため。サーバー側に認証を複製しない

### 3.3 認証

- Phase 1: 旅行ハブと同じPIN方式（ハッシュのみ埋め込み・端末に記憶）＋Supabase anonキー＋RLS。単一ユーザー前提
- Phase 2以降: Supabase Auth（Googleログイン）に置き換え可能な形にしておく（テーブルに owner 列を最初から持つ）

### 3.4 オフラインと同期

- 書き込みは必ずローカル（IndexedDB）に先に落とす。UIはローカルだけを見る
- 同期は「行ごと」ではなく「フィールドごとの更新時刻」で最終更新勝ち。Tina一人が2端末で使う程度なので、これで衝突は事実上起きない
- 同期失敗は画面上部に小さく「未同期 3件」とだけ出す。通知しない

### 3.5 時刻

- 保存はUTC。表示は端末のタイムゾーン。定例の「日曜22:00」などは rules に IANA タイムゾーンを持たせ、ジョージア滞在中は `Asia/Tbilisi` に切り替える（rules.timezone）

## 4. データモデル（Supabase）

すべてのテーブルに `id`, `owner`, `created_at`, `updated_at`, `field_updated_at jsonb`（フィールド単位の更新時刻・同期用）を持つ。以下は固有列だけ。

| テーブル | 役割 | 主な列 |
|---|---|---|
| `days` | 1日1行。紙の手帳の「日付ページ」 | `date`（一意）, `location`（京都／ジョージア／移動）, `theme`, `three_lines`（text[3]）, `mood`, `wins`, `carry_over`（text[]）, `morning_hub_url`, `evening_hub_url`, `houiban_image_url`, `moon_note`, `direction_alert` |
| `tasks` | タスクの正本（Phase 2から） | `title`, `project_id`, `scheduled_for`（date）, `due`, `status`（todo／doing／done／dropped）, `priority`, `carried_from`（date）, `source`（hub／todo_md／app／agent）, `done_at`, `note` |
| `projects` | プロジェクトボード | `name`, `flow`（伝える／旅／学び／土台／共創／暮らし）, `status`（進行中／仕込み中／運用中／未着手／止まってる／受け身／完了）, `next_action`, `next_milestone`（date）, `milestone_note`, `links`（jsonb: ローカルパス・Notion URL）, `reviewed_this_month`（bool）, `notion_page_id` |
| `events` | 年間イベント（大きな石）＋カレンダー同期分 | `title`, `start`, `end`, `all_day`, `kind`（旅・移動／ツアー・事業／法人・手続き／打合せ・イベント／記念日・家族／期限／節目／カレンダー）, `flow`, `certainty`（確定／予定／検討中）, `source`（gcal／plan／app）, `gcal_id`, `gcal_calendar_id`, `note` |
| `routines` | 定例（データとして持つ） | `title`, `scope`（daily／weekly／monthly／yearly）, `rrule`（RFC5545）, `time`, `timezone`, `owner_agent`（秘書／サン／ボウ／ララ／けいちゃん／Tina）, `active`, `note` |
| `routine_logs` | 定例の実施記録 | `routine_id`, `date`, `done`, `note` |
| `habits` / `habit_logs` | 習慣（Daily Log 2026 DBの11項目を移行） | `habits.title`, `habits.order` / `habit_logs.habit_id`, `date`, `done` |
| `weeks` | 週の型 | `week_start`（月曜）, `lead`（今週の主役）, `moving_days`（text[]）, `night_slots`（jsonb）, `body_bookings`（text[]）, `language_theme`, `projects`（uuid[2]）, `not_doing`, `sunday_close`（jsonb: done1／carry1） |
| `months` | 月間ページ | `month`（YYYY-MM）, `season`, `theme`, `big_moves`, `focus`（text[3]）, `location`, `review`（jsonb: best／progressed／stalled／temperature／carry3／dropped）, `review_status` |
| `notes` | 手書き・自由メモ | `page_ref`（day:YYYY-MM-DD／week:YYYY-Www／month:YYYY-MM／project:uuid）, `strokes`（jsonb・SVG path配列）, `text`, `thumbnail_url` |
| `rules` | Tina固有の設定（コードに書かない） | `key`, `value`（jsonb）。例: `flows`（5つの流れ）, `seasons`（手帳の季節）, `honmeisei`（三碧木星）, `timezone`, `georgia_183`（滞在実績と計画）, `night_slots`（21:00枠の並び）, `pin_hash` |
| `jobs` | 下位エージェントへの依頼キュー | `kind`（sync_calendar／draft_week／draft_month_review／mirror_notion／trip_prep／...）, `payload`, `status`（queued／running／done／failed）, `requested_by`（tina／app／schedule）, `result`, `agent` |
| `sync_log` | 同期の記録（障害調査用） | `source`, `started_at`, `finished_at`, `ok`, `message` |

設計上の決めごと:
- **予定（events.source=gcal）はアプリから編集しない。** 編集はGoogleカレンダーで。アプリで書けるのは「大きな石」（source=plan／app）だけ
- **タスクと予定は別テーブル。** 週画面で同じ列に並べて見せるが、混ぜて保存しない（デジタル手帳で捨てた「圧迫」を避ける）
- `days.three_lines` は3要素固定。4行目は入力できない（憲法2）
- `rules` は上位エージェントが構成変更で触る唯一の場所。下位はここを変えない

## 5. 画面（紙の手帳の「インデックス」に合わせて4つ）

画面は4つだけ。下部タブで切り替える。すべての画面に共通して、上部に「今日の日付・所在・同期状態」を1行。

### 5.1 今日（Today）

朝ハブの要約を「読む」画面と、1日3行を「書く」画面を1枚にする。開いて10秒で閉じられること。

```
┌──────────────────────────────┐
│ 2026-09-23（水）秋分  京都  ●同期済    │
│ 今日のテーマ: 秋分の折り返し           │  ← 朝ハブから
├──────────────────────────────┤
│ 予定  11:00 脱毛 / 21:00 説明会 / 22:00 打合せ │  ← Googleカレンダー
│ 3大   □ 一括払い手続き  □ EQ引き出し  □ 管理表  │  ← 朝ハブのMIT（Phase2: tasks）
├──────────────────────────────┤
│ [方位盤 画像]  吉=南西 注意=南・西・東   │  ← tina-hub-images
├──────────────────────────────┤
│ 今日の3行                              │
│  1 ______________________________     │
│  2 ______________________________     │
│  3 ______________________________     │
│ 習慣  ○朝ストレッチ ○語学 ○お茶時間 …    │  ← habit_logs
├──────────────────────────────┤
│ 夜  気分 ☀️🌿🌫🌧   よかったこと ______   │  ← 夕ハブへ渡す（Phase2）
│     繰越 □ □ □（チェックで明日へ）        │
└──────────────────────────────┘
```

- 朝は上半分だけ見る。夜は下半分だけ書く。スクロール1回で全部
- 「今日の3行」はプレーンテキスト。iPadでは手書きレイヤーに切り替えられる（notes.page_ref=day）
- 左右スワイプで前日・翌日（紙をめくる感覚）

### 5.2 週（Week）

紙の週間見開き。左ページが「週の型」、右ページが7日の列。日曜の夜に左を書き、平日は右を見る。

```
┌────────────────┬───────────────────────────┐
│ 週の型（左ページ）      │ 月  火  水  木  金  土  日          │
│ 今週の主役: ________  │ 予定（gcal）が時間順に薄く          │
│ 動く日: 立川 10/3-4    │ タスク（tasks.scheduled_for）が濃く  │
│ 夜21:00枠: 月zoom 水金EQ│ 定例（routines）は行頭にマーク     │
│ 身体: Rintosull 10/8  │ ごみの日は最上段に小さく            │
│ 語学: 英語（10週間）    │                                   │
│ 進めるPJ: ①____ ②____ │                                   │
│ やらないと決めた: ____  │                                   │
│ 日曜の締め: 済1 送1     │                                   │
└────────────────┴───────────────────────────┘
```

- スマホでは左右ページを上下に。iPad横向きで見開き
- 「進めるPJ」は2枠固定。3つ目は入れられない（週の型の思想）
- タスクは右ページで日をまたいでドラッグできる（紙で矢印を引く操作）

### 5.3 月／年（Month / Year）

- **月**: 上に月間カレンダー（大きな石だけ表示。gcalの細かい予定は点で）。下に「今月の焦点3つ」「プロジェクトの節目」「月次の定例表（済チェック）」「月末レビュー」。Notionの月間ページと同じ順
- **年**: 16ヶ月の帯（2026.09〜2027.12）。季節を色帯で、大きな石を帯の上に置く。183日カウンターと5年の航海の現在地を右端に固定表示。ピンチで四半期・月に寄れる

### 5.4 プロジェクト（Projects）

- ボード表示（状態別／5つの流れ別を切替）。カードは「名前・流れ・次の一手・次の節目」の4要素だけ
- カードを開くと、次の一手の履歴（日付つき追記）、紐づくタスク、関連リンク（ローカルパス／Notion）、手書きメモ
- 月初に「見直し済」が全部外れ、月末レビューで付け直す（Notion手帳と同じ運用）

### 5.5 設定（タブにしない・右上の歯車）

- rules の編集（タイムゾーン切替、5つの流れ、季節、定例の並び）。定例（routines）の一覧と有効／無効
- データ書き出し（JSON・月間ページのMarkdown）

## 6. 手書きレイヤー（紙の良さを一番担う部分）

- iPad＋Apple Pencil を主対象。iPhone・Macでは表示のみ（描くこともできるが主用途ではない）
- Pointer Events（pressure・tilt）で描き、SVG path として `notes.strokes` に保存。ラスタ化しない（拡大しても崩れない・軽い）
- 描ける場所: 今日の3行の裏面、週の左ページ、月間ページの余白、プロジェクトカードのメモ。それ以外には描けない（何でも描けると紙のノートと同じ散らかり方をする）
- 色は墨茶1色＋金1色（Bonnur調）。消しゴムとUndoだけ。ペン種は増やさない
- 文字認識・検索はしない（Phase 3で検討）。手書きは「書く儀式」のためで、検索はテキストの3行が担う

## 8. Phase分け

| Phase | 期間の目安 | 作るもの | 完了の定義 |
|---|---|---|---|
| 0 構成 | 済（この文書） | 設計書・データモデル・画面 | Tinaが4画面の骨格に「これでいい」と言う |
| 1 読む手帳（MVP） | 3週間 | 今日／週／月／年の表示。カレンダー同期。Notion手帳の初期インポート。PIN。PWA・オフライン閲覧。書けるのは「今日の3行・習慣チェック・週の型・月の焦点」だけ | 1週間、朝と日曜夜に開いて困らない。ジョージア年末滞在（12/21〜）で機内・現地オフラインでも読める |

## 10. リスクと対策

| リスク | 対策 |
|---|---|
| Googleカレンダーの取得失敗（`calendarId` 抜け・複数カレンダー漏れ・tentative漏れ） | morning-hub スキルに蓄積された事故ルールをそのまま同期スクリプトに実装。取得失敗は sync_log に残し「予定なし」と書かない |
| Mac が寝ている・ネット未接続で同期が止まる | launchd は wait_for_network。アプリは「最終同期 ◯時間前」を常に表示し、24時間超で Telegram 1回だけ |
| 2端末で同時編集 | フィールド単位の最終更新勝ち。同時編集が現実に起きるのは週の型くらいなので許容 |
| PIN方式の弱さ | 単一ユーザー・RLS・個人情報は days／notes に限定。公開情報（EQ額・口座）は入れない。Phase 2 で Google ログインへ |
| 手書きデータの肥大 | SVG path・ページ単位で分割保存・サムネイルはクライアント生成 |
| Notionミラーの二重編集 | ミラー先ページの先頭に「正本はアプリ」のコールアウト。Notion側の編集は拾わない |
| 作り込みすぎ | 4画面固定。5画面目の提案は上位に戻す（憲法7） |
